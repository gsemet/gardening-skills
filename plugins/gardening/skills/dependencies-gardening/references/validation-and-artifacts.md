# Validation and dependency artifacts

Use project evidence to choose commands and determine which files must be
regenerated. Never substitute a familiar language-specific command for the
repository's documented workflow without explaining the deviation.

## Discover quality gates

Inspect, in order:

1. `AGENTS.md`, `CONSTITUTION.md`, contribution guidance, and accepted ADRs;
2. task runners such as `justfile`, `Makefile`, or package scripts;
3. CI configuration and reusable CI templates;
4. package-manager metadata and project configuration; and
5. recent documented developer workflows.

Identify both focused checks and the broadest project gate. Focused checks should
cover the changed subproject or dependency surface. The broad gate should cover
integration, packaging, documentation, and other checks the project defines as
required before completion.

Do not invent a preflight target. If no reliable gate is documented, report that
fact and use only the package manager's clean resolution plus any directly
available focused checks.

## Artifact roles

Classify each dependency-related file as one of:

- **Declarative source**: edited through the project's approved mechanism.
- **Authoritative lock**: regenerated by the prescribed resolver command.
- **Derived dependency output**: regenerated only when project conventions or the
  final gate require it.
- **Generated report or cache**: do not hand-edit or include in the update.
- **Evidence only**: inspect for context but do not modify.

A lockfile is not automatically authoritative, and a manifest is not always the
only source of truth. Follow project evidence when declarations are dynamic,
generated, split into groups, or maintained by a tool.

## Command selection

Use the command already named by the project for each operation. Record the exact
command and working directory in the final report. Keep install and resolution
steps scoped to the update unit where the tooling permits it.

When a command needs a registry, proxy, certificate, credential, or special
runtime, use the project's documented environment setup. Do not expose secrets,
write them into repository files, or invent placeholder credentials. If the
required environment is unavailable, classify the result as environment-blocked.

## Validation sequence

For each update unit:

1. Verify the baseline state and preserve unrelated local changes.
2. Update the declaration through the approved project mechanism.
3. Regenerate the authoritative lock or derived artifact.
4. Run the narrowest relevant check.
5. Diagnose and isolate failures before proceeding.
6. Run the broad repository gate after all independent units are complete.

Repeat a focused check after each source adaptation. Do not skip the broad gate
merely because every focused check passed unless project guidance defines that
focused validation as sufficient.

## Generated files

Never hand-edit lockfiles, generated requirements, exported dependency lists,
SBOMs, package-manager metadata, or reports. Regenerate them with the owning
project command. If regeneration creates unrelated churn, restore only the
unrelated generated changes and record the issue rather than manually editing the
output.

## Environment and flaky checks

A registry outage, proxy error, missing executable, platform mismatch, or flaky
check is not evidence that a dependency is incompatible. Retry only when the
project convention permits a retry and record the result. If compatibility stays
unverified, revert the affected unit and report the environmental blocker.

## When to Load This Document

Load when discovering focused or broad quality gates; choosing project commands;
regenerating lockfiles; handling generated dependency artifacts; or
 distinguishing environment failures from compatibility failures.
